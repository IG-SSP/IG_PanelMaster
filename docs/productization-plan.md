# Productization Plan

## Цель

Сделать VPN-каскад расширяемым продуктом: один локальный оркестратор на Windows
хранит описание сети, генерирует серверные скрипты, применяет их к новым VPS по
SSH и позже станет основой для визуального приложения.

## Принцип

Источник правды должен быть один: `network.json`. Из него генерируются:

- WireGuard-конфиги ingress и exit-узлов;
- health-check и route-table конфигурация;
- конфигурация мониторинга;
- команды установки и обновления VPS.

Приватные ключи, токены Telegram, пароли и SSH-данные не должны попадать в git.
Для локального состояния используются `.vpn-state/` и `.vpn-secrets/`, которые
игнорируются через `.gitignore`.

## Этапы

1. CLI-оркестратор на PowerShell для Windows.
   - интерактивно спрашивает ingress, домен, IP, интерфейсы, exit-узлы;
   - пишет публичный манифест в `.vpn-state/network.json`;
   - пишет секреты только в `.vpn-secrets/network.secrets.json`;
   - генерирует shell-скрипты в `build/generated/`;
   - может загрузить и запустить выбранный скрипт через `scp`/`ssh`.

2. Нормализация текущих скриптов.
   - убрать hardcode списка exit-узлов из `cascade-monitor.py`,
     `cascade-health-hysteresis.sh`, `cascade-routing-new.sh`;
   - читать сгенерированный `/etc/cascade/network.json` или отдельные
     конфиги `/etc/cascade/exits.json`;
   - оставить текущие скрипты как проверенный runtime.

3. Безопасное применение изменений.
   - dry-run по умолчанию;
   - обязательный backup перед изменением `/etc/wireguard`, systemd, nftables;
   - явное подтверждение перед restart сервисов и firewall/routing изменениями;
   - health-check после применения;
   - fail-closed route при отсутствии рабочих exit-узлов.

4. Desktop/Web приложение.
   - frontend вызывает тот же backend-оркестратор;
   - экраны: topology, exits, client portal, мониторинг, deploy log, secrets
     status;
   - backend выполняет SSH-команды, хранит секреты в локальном защищенном
     хранилище Windows или в зашифрованном файле.

## Почему сначала CLI

Визуальное приложение лучше строить поверх уже стабильной модели данных и
операций. Если сразу делать UI, появится риск повторить текущую проблему:
логика будет размазана между кнопками, shell-фрагментами и ручными действиями.

## Минимальная модель продукта

- `config/network.example.json` - пример манифеста.
- `tools/vpn-orchestrator.ps1` - первый интерактивный Windows-оркестратор.
- `.vpn-state/network.json` - локальный рабочий манифест.
- `.vpn-secrets/network.secrets.json` - локальные приватные ключи и токены.
- `build/generated/*.sh` - скрипты, которые можно прочитать перед запуском.

## Риски для реального оборудования

- Ошибка в `publicInterface` на exit-узле ломает NAT.
- Ошибка в `AllowedIPs` или table/rule может пустить трафик напрямую или
  оборвать клиентов.
- Restart `wg-quick`, `nftables`, `docker`, `caddy` на боевом ingress нужно
  делать только после просмотра сгенерированного скрипта.
- Текущие Amsterdam-узлы с проблемным SSH нельзя автоматически обновлять, пока
  не решена причина закрытия SSH-сессии.
